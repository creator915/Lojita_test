# Runtime NbE 长任务执行计划

## 目标与自治边界

Codex 持续执行“观察 → 选择最小可验收切片 → 实现 → 验证 → 记录新状态”的循环，
不在每个点位完成后请求确认。正常的源码编辑、测试、诊断、可恢复的构建产物和文档更新
均属于已授权范围。

仅在以下情况暂停并请求用户决策：

- 需要改变根验收目标、删除既有能力或让三条路径产生源码依赖；
- 需要新增未经批准的外部服务、凭证、付费资源或高风险副作用；
- provider 的语义/许可证使既定范围不可实现，需要更换 provider 或缩减支持面；
- 同一外部阻塞在穷尽安全替代方案后仍无法推进；
- 用户明确暂停、取消或改变目标。

不因单个测试失败暂停。失败应先分类、最小化复现、修复或建立 fail-closed 边界，然后继续。
不自动提交、推送、改写历史或创建 PR；提交仍遵循仓库授权与单一目的要求。

## 成功终态

正式完成由根 `ACCEPTANCE.md` 的 Runtime NbE 八项共同定义。Codex 不根据自行维护的计划、
测试数量或局部演示宣布完成。最终证据必须来自指定 commit 的可重复测试和独立核验。

## 持久状态

- `ACCEPTANCE.md`：唯一正式进度来源。
- `runtime-nbe/CAPABILITY-MATRIX.md`：技术覆盖、真实场景和证据索引。
- `runtime-nbe/README.md`：架构、支持边界与操作入口。
- 测试输出：commit、输入身份、依赖身份、工具版本、逐项结果和退出码。

每次改动后更新矩阵，但只有完整满足根验收定义时才更改根清单。对话上下文压缩或任务跨多轮
时，以上文件而非历史聊天承担恢复作用。

## 执行状态机

1. **OBSERVE**：读取当前 SHA、工作树、矩阵、最近失败和可用依赖。
2. **SELECT**：选择一个能减少关键风险的最小纵向切片；优先修复验证基础设施和公共骨架。
3. **BASELINE**：先运行相关现有测试并保存失败分类，确认不是陈旧产物。
4. **IMPLEMENT**：只修改该切片必要的生产路径和测试，不用分流器或 fixture 特判掩盖缺口。
5. **VERIFY**：运行真实正例、输入敏感对照、fail-closed 反例、资源边界、差分和受影响回归。
6. **RECORD**：更新矩阵、README 和可重复命令；检查差异与生成物。
7. **CONTINUE**：成功则自动选择下一切片；可恢复失败回到 OBSERVE；外部阻塞才进入 WAITING。

重复动作或同一失败连续出现时，先改变诊断方法或缩小复现，不无限重跑。任何完成声明必须由
程序化终态检查支持。

## 阶段顺序

### A. 证据基础设施

1. 复现 Web ELF 符号失败，识别 GHC 优化、符号可见性和 `nm` 方言差异。
2. 将精确别名字符串检查替换为跨平台且能证明真实链接/调用的组合证据。
3. 把 Web 失败固定为回归，并确保错误不会被行为测试的 PASS 掩盖。
4. 解决 `primdata` 许可证证据；无法解决时实现正式发布 fail-closed 门禁。

### B. 通用数据闭环

1. 定义版本化 runtime packet：真实 Agda `Term + Type`、最小定义切片、上下文和 provider 身份。
2. 实现通用 reflect 层，消除围绕单个 Bool `primHComp` 的专用通道。
3. 实现 provider normal form 到 Agda Term 的 reify。
4. 在结果发布前执行 recheck，并保证失败不留下半成品。
5. 通过公开接口接入 MAlonzo 最终用户程序，同时保持运行时无 Agda 子进程。

### C. 语义纵向切片

默认按依赖和风险顺序推进：`Pi` → record/Sigma → `transp` → 活动面 `hcomp` → `Glue` → HIT。
若能力探测证明 provider 的实际依赖顺序不同，可调整实现顺序，但必须在矩阵中记录理由，
不得静默缩减最终验收面。

每个构造都执行完整闭环，不先批量实现 reflect、最后统一补 reify/差分。现实场景、成功终态和
反例以能力矩阵为准，并在实现前细化成可程序化判断的 fixture。

### D. 资源与差分

资源边界随每个切片同步实现，最后统一验证 packet 大小、fuel、递归深度、allocation、超时、
临时文件清理和稳定错误码。差分必须把同一 Agda 输入送到真实 Agda oracle 与 runtime provider，
比较结构化 normal form；证明关联和手写期望仅作为补充。

### E. 环境与交付

1. 本目录独立测试全部通过。
2. 受影响的集成测试通过，且三条路径没有源码或可变产物依赖。
3. 指定 commit 在至少两个宿主环境复现。
4. Web 核验者 fresh clone 后检查真实数据流，并执行正例和反例。
5. 只有证据完整后才更新 `ACCEPTANCE.md`。

## 现实测试门槛

每个正例必须具备业务可解释的输入和终态，并至少满足以下四项：

- 输入来自真实、多定义或结构化 Agda 源码，而不是 verifier 参数选择的预制答案；
- 两个有效输入通过同一代码路径产生不同结果，证明输出对输入敏感；
- 最终用户程序消费结构化结果完成一个可观察任务，而不是只打印内部 AST；
- oracle、runtime 和 recheck 使用同一输入身份，测试会检测偷换 fixture 或陈旧产物。

每个切片至少包含正常、边界、恶意/损坏、资源超限四类案例。测试优先使用确定性程序验证，
不使用 LLM 判断语义正确性。

## 失败分类与纠正

| 类型 | 处理 |
| --- | --- |
| 实现错误 | 最小化真实复现，修复生产路径并加入回归。 |
| verifier 脆弱 | 保留原失败样本，改用跨环境稳定且不降低证据强度的检查。 |
| provider 不支持 | 能力探测后实现明确 adapter 或 fail-closed；若影响约定语义面则升级为用户决策。 |
| 工具/依赖缺失 | 输出 `NOT-RUN` 和实际探测信息，尝试参数化替代环境，不切换 mock。 |
| 许可证阻塞 | 禁止发布产物，保留本地技术验证与明确门禁。 |
| 资源/超时 | 终止当前案例、清理临时产物、记录限制，不无限提高配额。 |
